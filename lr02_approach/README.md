## 2. Кейс C-1

Конфлікт критеріїв: Більшість критеріїв (requirements, release_cost, customer, contract, team) тягнуть у предиктивний бік: вимоги зафіксовані регулятором, контракт fixed price за тендером із 2-тижневими погодженнями додаткових угодах, замовник відповідає 3–5 днів та вимагає актів за етапами, а ціна помилки — штрафні приписи для клієнтів. Головний конфлікт створює критерій technology: API державного реєстру запущено нещодавно, документація неповна, а поведінка методів змінювалася двічі за квартал без оголошення. Переміг предиктивний підхід, оскільки юридичні та фінансові ризики невиконання контракту з фіксованими строками переважають технологічну нестабільність.

Що робимо з критерієм, який тягне проти: Ізолюємо інтеграційний шар за допомогою патерну «Адаптер», розробляємо локальні моки API на основі специфікації та ведемо розробку відносно них, а тестування на живому контурі реєстру проводимо лише у заздалегідь визначені контрольні точки.

Відкинутий підхід: Для адаптивного підходу плюсом була б висока гнучкість розробки та можливість швидко перебудовувати архітектуру при раптових змінах API реєстру без бюрократичних процедур. Проте його мінусом є те, що недоступний замовник (відповідь 3–5 днів) та fixed price контракт із штрафами за прострочення перетворили б будь-яку гнучкість на прямі фінансові збитки підрядника.

Перший тиждень: PM проводить спільний архітектурний воркшоп із командою та аналітиком для розробки моків нестабільного API реєстру, зафіксує рамки ТЗ та узгодить із замовником чіткий графік 3-етапного приймання за актами.

## 3. Кейс C-2

Конфлікт критеріїв: Критерії requirements, customer, contract, team та technology однозначно тягнуть в адаптивний бік: вимоги змінюються кожні два тижні за результатом інтерв'ю, замовник-співзасновник сидить в одній кімнаті, зовнішнього договору немає, команда крос-функціональна, а автоматизований відкат займає 10 хвилин. Головний конфлікт створює release_cost: помилка у розрахунку комісій чи застав призводить до ручних повернень, скарг, відгуків та ризику перегляду умов з боку банку-еквайра. Адаптивний підхід переміг, оскільки стартап не має річного плану і повинен швидко перевіряти гіпотези для збереження інвесторського бюджету.

Що робимо з критерієм, який тягне проти: Виділяємо платіжний та розрахунковий контур в окремий релізний цикл із обов'язковим автоматизованим регресійним тестуванням фінансових формул та суворим перехресним код-рев'ю.

Відкинутий підхід: Для предиктивного підходу плюсом була б максимальна юридична та фінансова гарантія відсутності помилок у розрахунках за рахунок довгого циклу проектування та заморозки вимог. Однак його мінусом є повна втрата ринкової адаптивності стартапу та ризик спалити бюджет інвестора на функціонал, який виявиться непотрібним ринку.

Перший тиждень: PM виділяє платіжний та розрахунковий контур в окремий релізний цикл із суворим автоматизованим регресійним тестуванням, налаштовує CI/CD та запускає 2-тижневі спринти з демо щоп'ятниці.

## 4. Кейс C-3

Конфлікт критеріїв: Критерії requirements (приховані винятки в процесах), technology (недокументована legacy-база) і team (мала зіграна команда) тягнуть в адаптивний бік. Натомість contract (fixed price, річний бюджет без можливості збільшення) та release_cost (помилка нарахування виявляється після виплат) тягнуть у предиктивний бік. Переміг гібридний підхід, оскільки він дозволяє тримати жорстку предиктивну рамку за бюджетом і строками, але розробляти та уточнювати недокументовані бізнес-процеси адаптивно всередині ітерацій.

Що робимо з критерієм, який тягне проти: Впроваджуємо гнучку пріоритизацію за MoSCoW в межах зафіксованого бюджету: критичний функціонал (Must Have) реалізується за жорстким ТЗ, а складні винятки погодження (Should/Could Have) реалізуються в межах залишку ресурсів.

Відкинутий підхід: Для предиктивного підходу плюсом була б повна юридична визначеність для фінансового директора та прозора фіксація обсягу робіт на самому початку. Проте його мінусом є високий ризик розробки системи, яка не відповідатиме реальним прихованим процесам юристів і застрягне на міграції даних зі зіпсованої legacy-бази.

Перший тиждень: PM організовує аудит вивантаження даних зі старої бази, зафіксує базовий реєстр винятків у погодженні договорів із юридичним відділом та погодить із фіндиректором процедуру пріоритизації вимог.

## 5. Стрес-тест контрактом

Конверт зі зміною умови лежить у кінці `lr02_cases.md` і відкривається після
того, як заповнено `decision.csv`. Запишіть, яким рішення було до конверта і що
зсунулось після нього.

| Кейс | Рішення до конверта | Рішення після | Що змінилось у роботі PM |
| :-: | --- | --- | --- |
| C-1 | predictive, main_conflict: technology | predictive, main_conflict: technology | Звільнення підрядника від фінансового ризику перевитрати бюджету; перехід від монолітного акта до щотижневих/щомісячних звітів про відпрацьований час (Timesheets) із демо на тестовому контурі; ризик зміни API переїхав із підрядника на замовника |

Окремо: що робить PM, коли контракт fixed price, а вимоги мінливі. Назвіть
щонайменше два робочі ходи і ціну кожного. 1) Впровадження Change Control Process із резервом обсягу (Scope Buffer): 80% бюджету фіксується на базове ТЗ, а 20% резервується під нові винятки спрощеним рішенням PM і замовника (ціна: скорочення початкового обсягу та складні переговори на старті). 2) Фазоване підписання специфікацій (Progressive Elaboration): підписання ТЗ окремими додатковими угодами на кожен етап за результатами попередньої аналітики (ціна: збільшення накладних витрат PM на регулярне узгодження документів з юристами).

## 6. Власний проєкт

Тема: Сервіс бронювання аудиторій (Варіант V02).

Обраний підхід: adaptive (Scrum).

Чому саме так: Команда з 4-5 осіб працює у 10-тижневий строк із доступним замовником (деканат/IT-відділ), який готовий до щодвотижневих демо. Адаптивний підхід ловить Ризик 2 з ЛР1 (пізня інтеграція з базою даних розкладу): роботу з API розкладу винесено вже на 2-й спринт, що дозволяє виявити розбіжності в типах даних на самому початку. На відміну від C-1 у нас немає жорсткого регулятора зі штрафами, на відміну від C-2 відсутні прямі фінансові ризики еквайрингу, а на відміну від C-3 відсутня 20-річна legacy-база без документації.

З чим ви живете далі:

| Що | Ваше рішення |
| --- | --- |
| Довжина ітерації | 2 тижні (всього 5 спринтів на 10-тижневий термін проєкту) |
| Події | Daily Standup (15 хв, щодня), Sprint Planning (2 год, раз на 2 тижні), Sprint Review & Demo (1 год, в кінці спринту), Retrospective (45 хв, після демо) |
| Дошка і WIP | Дошка у GitHub Projects / Trello з колонками: Backlog -> To Do (WIP: 5) -> In Progress (WIP: 3) -> Code Review (WIP: 2) -> Testing (WIP: 2) -> Done |
| Definition of Done | 1) Код пройшов перехресне Code Review (2 ока); 2) Юніт-тести пройдені успішно; 3) Функціонал розгорнуто на Staging-контурі; 4) Проведено QA-перевірку та оновлено API Swagger |
| Точка приймання | Представник деканату / IT-відділу вишу на Sprint Review після демонстрації працездатного приросту системи (Increment) на Staging |

## 7. Робочий журнал

Під час аналізу кейсу C-1 початкова думка схилялася до гібридного підходу через нестабільність API реєстру. Проте детальний розбір умов тендеру, fixed price контракту із двотижневим погодженням змін юристами та відсутності замовника на щотижневих демо показав, що PM змушений вести проєкт предиктивно, ізолюючи технологічні ризики через мокування API. Стрес-тест контрактом у розділі 5 підтвердив, що зміна контрактної моделі на T&M знімає фінансові ризики з підрядника, але не змінює жорстку зовнішню дату регулятора.
