## 1. Звідки взялася velocity

| Поле | Значення |
| --- | --- |
| Спринтів у `velocity.csv` | 2 |
| Тривалість спринта | два тижні |
| Ємність спринта з мого варіанта | 22–24 SP |
| Середня фактична velocity | 25 SP |
| Найгірший і найкращий спринт | 19 SP і 31 SP |

Звідки бралися points закритих історій: я взяв `final_estimate` з `lr08_poker/estimates.csv` і сумував історії, закриті в кожному спринті. Спринт 1: S-01 (3) + S-03 (3) + S-02 (5) + S-04 (8) = 19 SP. Спринт 2: S-06 (8) + S-07 (3) + S-05 (2) + S-09 (13) + S-11 (5) = 31 SP. Жодна історія в спринтах не відрізнялася від оцінок у `estimates.csv`.

Чому факт розійшовся з ємністю варіанта: ємність варіанта є орієнтиром для плану, а фактична velocity — це те, що реально вийшло в роботі. У цьому проєкті фактична швидкість була вищою за планову, бо вчасно закрили повний базовий цикл і не зафіксували критичних блокерів, тому обсяг REL-1 виявився виконаним до кінця другого спринту.

## 2. Як рахувалася симуляція

| Поле | Значення |
| --- | --- |
| Інструмент | власний Python-скрипт |
| Прогонів | 10 000 |
| Що тягнеться випадково | фактична velocity одного спринта з масиву [19, 31] |
| Дата, від якої відлічуються спринти прогнозу | для сценарію «весь перший реліз» — кінець спринта 1, для сценарію залишку — кінець спринта 2 |

```python
import math
import random

random.seed(42)
velocity = [19, 31]


def run_forecast(target_points):
    sims = []
    for _ in range(10000):
        total = 0
        sprints = 0
        while total < target_points:
            total += random.choice(velocity)
            sprints += 1
        sims.append(sprints)
    sims.sort()
    p50 = sims[math.ceil(0.50 * len(sims)) - 1]
    p85 = sims[math.ceil(0.85 * len(sims)) - 1]
    return p50, p85


# REL-1 = 50 SP
p50, p85 = run_forecast(50)
print(p50, p85)

# залишок після моїх двох спринтів = 0 SP
print(run_forecast(0))
```

У формулі дати я використав правило FC-3: різниця між `p85_date` і `p50_date` завжди дорівнює `(p85_sprints - p50_sprints) * 14 днів`.

## 3. Дві дати першого релізу

| Сценарій | Points | P50, спринтів | P85, спринтів | P50, дата | P85, дата |
| --- | :-: | :-: | :-: | --- | --- |
| Весь перший реліз | 50 | 2 | 3 | 2026-11-06 | 2026-11-20 |
| Залишок після моїх спринтів | 0 | 0 | 0 | 2026-11-06 | 2026-11-06 |

У сценарії «Залишок після двох спринтів» залишок дорівнює 0 SP, тому фактична дата завершення залишку — 2026-11-06: на кінець Спринту 2 перший реліз уже був виконаний у повному обсязі. Для сценарію «Весь перший реліз» обсяг дорівнює 50 SP від початку Спринту 1, тому P85 лежить на 2026-11-20 і відображає ймовірні затримки на тривалій дистанції від початку релізу.

Яку дату я називаю замовнику вголос і чому саме її: я назву 2026-11-20 з імовірністю 85% для повного циклу релізу, бо це дата для сценарію «Весь перший реліз» з урахуванням ймовірних затримок. Окремо, для завершеного залишку після двох спринтів, фактична дата завершення вже є 2026-11-06, і вона показує, що реліз фактично було виконано до кінця другого спринту.

## 6. Що я кажу замовнику

Дата вголос: для повного циклу релізу я назву 2026-11-20 з імовірністю 85%; окремо зауважу, що залишок після двох спринтів уже завершений фактично 2026-11-06, тому 2026-11-20 — це дата для сценарію «Весь перший реліз» з урахуванням ймовірних затримок, а не дата фактичного виконання залишку.

Коли я перерахую прогноз: я перерахую прогноз після закриття наступного спринта, якщо зміниться склад першого релізу, або якщо з’явиться нове обмеження, що вплине на фактичну velocity. Для залишку після двох спринтів повторний розрахунок не потрібен, бо він уже фактично дорівнює 0 SP і завершений 2026-11-06.
